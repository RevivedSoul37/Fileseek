Change-Diff Tracking — Implementation Plan

A build plan for the coding agent to add "what changed" summaries to the live file watcher — without requiring OS-level process tracking or full version history.

Note to the coding agent: this plan is written without direct access to the current codebase. Method names, exact function signatures, and existing helper utilities below are proposed conventions, not confirmed facts — verify each against src/modules/ before implementing, and adjust names to match whatever already exists in config.py, utils.py, and index_store.py.

01

Objective & Scope

Goal: when the live watcher (Phase 2) detects that a file's content changed, store a short, structured summary of what changed — not just that it changed — so the UI can show something like "12 lines added, 3 removed" next to the existing "changed 3 hours ago" timestamp, with zero AI/LLM calls involved.

Explicitly not in scope for this plan: identifying which application or process caused the change (that needs OS-level handle tracking and is a separate, much larger effort — see §Out of Scope), and full version history / rollback (that needs full snapshots, not just diffs).

02

New Files

These slot into the watcher/ folder already scaffolded in the repo.

src/modules/watcher/diff.py
New module

Computes a lightweight diff summary between a file's previous and current state.

  • For text-based files (code, json, md, csv, txt): line-level diff using Python's built-in difflib — no new dependency needed.
  • For binary/non-text files (images, media, archives): no line diff possible — fall back to size delta + modified-time only.
  • Output: a small dict, e.g. {"lines_added": 12, "lines_removed": 3, "size_delta_bytes": 480, "summary": "12 lines added, 3 removed"} — exact keys should match whatever convention utils.py already uses for other metadata dicts.
  • Must cap how much it reads/diffs for very large files (reuse whatever excerpt/size limit the embedder already applies, so this doesn't become the slow part of a sync pass).
src/modules/watcher/snapshot_store.py
New module

Keeps just enough of the "before" state to diff against — not a full file history.

  • Store a content hash (for change detection — did it actually change, or just get touched/resaved identically) plus, for text files only, the last known line count and a small trimmed copy (same size cap as above) for diffing.
  • For non-text files: hash + size only, no content copy.
  • Persist this next to the existing FAISS index/metadata files (same data/ directory convention already used for index.faiss and metadata), not as a separate database, unless the agent finds a strong reason to split it.
03

Existing Files Touched

src/modules/watcher/sync.py
Planned Phase 2 file — logic to add

Where the actual hook goes: whenever a modify event comes through the event queue, before overwriting the index entry, call snapshot_store to fetch the previous snapshot, run diff.py against the new content, then write the diff summary into that file's metadata entry alongside its existing fields (name, path, category, etc.) — reuse the existing add_or_update-style method on IndexStore if one exists, extending its record shape rather than adding a second write path.

src/modules/core/utils.py
Likely touched

If there's already a shared "record shape" helper or constant listing metadata fields (used by crawler.py and the verification suite), the new diff fields need to be added there too, so verify_build.py-style checks that assert "record has all fields" don't need separate maintenance later.

Frontend — result card template / app.js
UI change

Add a small line under the existing "modified X ago" text on each result card, showing the diff summary when present (e.g. "12 lines added, 3 removed"). Hide it entirely for files with no diff data yet (first index pass, or binary files) rather than showing an empty or misleading line.

04

Data Model — Proposed Metadata Addition

Per-file, in addition to existing fields (name, path, category, size, modified, sensitive, etc.):

FieldTypeNotes
last_diff_summarystring or nullHuman-readable line, e.g. "12 lines added, 3 removed". Null until the file has changed at least once after initial indexing.
last_diff_lines_addedint0 for binary files.
last_diff_lines_removedint0 for binary files.
last_diff_size_deltaint (bytes, signed)Always computable, even for binary files.
content_hashstringUsed internally by snapshot_store to detect real vs. no-op changes; not necessarily shown in UI.
05

Build Sequence

1
Confirm existing conventions first

Before writing new code, the agent should read config.py, utils.py, and index_store.py to confirm the actual metadata record shape, the actual method names for adding/updating index entries, and whatever size/excerpt limits the embedder already enforces — reuse these rather than inventing parallel conventions.

2
Build snapshot_store.py

Implement hash-based change detection first, in isolation, with its own small test — this is the foundation everything else depends on.

3
Build diff.py

Implement the line-diff for text files and the size-delta fallback for binary files, tested against a few sample files independently of the watcher.

4
Wire into sync.py

Only once 2 and 3 are independently verified, hook them into the actual modify-event handling path.

5
Update the metadata schema + verification suite

Extend verify_build.py-style checks to assert the new fields exist and behave correctly (e.g. stay null until a real change happens).

6
Surface it in the UI

Last step, once the data is reliably there — add the frontend line described in §3.

06

Edge Cases To Handle

  • No-op saves: some apps rewrite a file with identical content on save (common with editors/IDEs). The content hash check must prevent these from generating a false "changed" diff.
  • Rapid successive edits: if the event queue batches multiple modify events for the same file before sync runs, diff against the oldest available snapshot, not an intermediate one, so the summary reflects the real net change.
  • First-time index vs. real change: a file appearing in the index for the first time should never get a diff summary — that's not a change, that's discovery.
  • Very large text files: respect the same excerpt/size cap used elsewhere so diffing a huge log file doesn't stall the sync queue.
  • Renamed vs. modified: a pure rename (same content, new path) should not produce a content diff — only a path-change note, if one exists elsewhere in the metadata already.
07

Verification Checklist

  • Modify a text file → diff summary appears with correct added/removed line counts.
  • Re-save a text file with no actual content change → no new diff summary generated.
  • Modify a binary file (e.g. an image) → size-delta-only summary appears, no line counts.
  • Newly discovered file on first index → no diff summary present.
  • Rename a file without changing content → no diff summary triggered by the rename alone.
  • Large file (above the size cap) → diff still completes without noticeably slowing the sync queue.

Explicitly Out of Scope for This Plan

  • Which app/process caused the change — requires OS-level file handle or process tracking (e.g. Windows ETW/Process Monitor-style hooks), needs elevated permissions, and is a separate, much larger effort. A cheap approximation (logging the foreground app when watchdog fires) could be a later stretch goal, not part of this build.
  • Full version history / rollback — would require storing full file snapshots over time, which conflicts with keeping the index lightweight (~26MB currently for 13.5k files). Only worth revisiting if users explicitly ask for it on specific folders.
